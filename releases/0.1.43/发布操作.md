# 0.1.43 内部发布包与上线操作

面向生产入口 `https://nuotop.xyz`，沿用项目现有 internal MSI 分发方式。未启用 TUF 自动更新，不是 Authenticode 签名发行版。版本目录为不可变产物，已存在的旧版本不覆盖。

## 产物与来源

- `CodexRemoteAgent.msi`：Windows x64、当前用户安装。
- `internal-release.json`：安装包版本、下载地址、SHA256、来源基线。
- `SHA256SUMS.json`：发布文件校验和。
- `build-evidence.json`：本次构建/解包/实际运行验收结果及明确边界。
- `source-files.sha256.json`：构建时产品源码与打包输入的逐文件摘要，补充未提交工作区构建的来源证据。

此次按用户要求先构建、后提供提交命令，因此 manifest 的 `source_revision` 是构建时 HEAD，`source_dirty=true` 是事实。不要事后将它手改成“由新提交的干净源码构建”。后续若要求 clean-commit 构建，应从已提交代码用新的未占用版本重建。运行逻辑与12小时长测来源的关系见 build-evidence。

本轮没有自动提交、推送、创建 GitHub Release、安装 Agent 或更新服务器。下面命令由用户按顺序执行。

## 一、提交后端和前端（本机 PowerShell）

后端与前端均在 `main`，发布仓库在 `master`。命令仅暂存本任务涉及的代码/配置/验收工具与三份交付文档，不使用 `git add -A`，避免带入工作区既有的大量文档迁移。先确认暂存区没有其他任务内容。

```powershell
$ErrorActionPreference = 'Stop'
Set-Location E:\python_web_fastapi\work
if ((git branch --show-current) -ne 'main') { throw '后端当前分支不是 main' }
if (git diff --cached --name-only) { throw '暂存区已有内容，请先核对归属' }
git add -- src config/runtime/codex_control_runtime config/runtime/stream_runtime deploy/caddy/Caddyfile.example scripts/codex/acceptance scripts/codex/autotuner/connection 'docs/design_docs/Codex连接与执行生命周期加固.md' 'docs/design_docs/Codex连接加固上线环境检查.md' 'docs/design_docs/Codex连接加固发布0.1.43.md'
if ($LASTEXITCODE -ne 0) { throw '后端暂存失败' }
git diff --cached --stat
git commit -m 'fix: harden Codex connection lifecycle and prepare Agent 0.1.43'
if ($LASTEXITCODE -ne 0) { throw '后端提交失败' }
$backendRevision = (git rev-parse HEAD).Trim()
git push origin main
if ($LASTEXITCODE -ne 0) { throw '后端推送失败；不要强推' }
Write-Host "BACKEND_REVISION=$backendRevision"

Set-Location E:\python_web_fastapi\typescript-web-nuxt
if ((git branch --show-current) -ne 'main') { throw '前端当前分支不是 main' }
if (git diff --cached --name-only) { throw '暂存区已有内容，请先核对归属' }
git add -- app tests/e2e/codex-connection.spec.ts
if ($LASTEXITCODE -ne 0) { throw '前端暂存失败' }
git diff --cached --stat
git commit -m 'fix: separate Codex connection recovery from history loading'
if ($LASTEXITCODE -ne 0) { throw '前端提交失败' }
$frontendRevision = (git rev-parse HEAD).Trim()
git push origin main
if ($LASTEXITCODE -ne 0) { throw '前端推送失败；不要强推' }
Write-Host "FRONTEND_REVISION=$frontendRevision"
```

若 push 因远端新提交失败，先处理差异，禁止强推覆盖。以上目录按构建时工作区归属核对；若之后有其他开发混入，先拆分后再暂存。

## 二、提交并发布安装包（本机 PowerShell）

`git push` 只上传仓库文件，**不会自动创建 manifest 中 URL 指向的 GitHub Release 附件**。必须完成本节 GitHub 网页手动发布后，才部署后端中的新下载入口。

按用户要求，0.1.43 由用户在 GitHub 网页手动发布；本说明不执行或要求自动创建 Release，也不需要安装 GitHub CLI。

先提交发布仓库：

```powershell
$ErrorActionPreference = 'Stop'
Set-Location E:\python_web_fastapi\codex-remote-agent-releases
if ((git branch --show-current) -ne 'master') { throw '发布仓库当前分支不是 master' }
if (git diff --cached --name-only) { throw '暂存区已有其他内容，请先核对' }
$releaseDir = Join-Path (Get-Location) 'releases/0.1.43'
$checksums = Get-Content "$releaseDir/SHA256SUMS.json" -Raw | ConvertFrom-Json
foreach ($entry in $checksums.PSObject.Properties) {
    $actual = (Get-FileHash -LiteralPath (Join-Path $releaseDir $entry.Name) -Algorithm SHA256).Hash.ToLowerInvariant()
    if ($actual -ne $entry.Value) { throw "校验失败：$($entry.Name)" }
}
git add -- releases/0.1.43
if ($LASTEXITCODE -ne 0) { throw '发布产物暂存失败' }
git diff --cached --stat
git commit -m 'release: Codex Remote Agent 0.1.43'
if ($LASTEXITCODE -ne 0) { throw '发布仓库提交失败' }
git push origin master
if ($LASTEXITCODE -ne 0) { throw '发布仓库推送失败；不要强推' }
```

然后打开 <https://github.com/1nuo123/codex-remote-agent-releases/releases/new>：

1. 新建 tag **v0.1.43**，Target 选择刚推送的 `master` 提交；标题 `Codex Remote Agent 0.1.43`。
2. 上传本目录的 `CodexRemoteAgent.msi`、`internal-release.json`、`SHA256SUMS.json`，以及 `build-evidence.json`、`source-files.sha256.json`。
3. 发布说明写明连接/执行生命周期加固；本包属于 internal 手动更新方式，不是签名自动更新发行版。
4. 手动点击 **Publish release**。若 tag/Release 已存在，先核对归属，禁止覆盖旧附件。
5. 确认下面两个地址可下载，再执行服务器更新：
   - <https://github.com/1nuo123/codex-remote-agent-releases/releases/download/v0.1.43/CodexRemoteAgent.msi>
   - <https://github.com/1nuo123/codex-remote-agent-releases/releases/download/v0.1.43/internal-release.json>

历史版本目录中还有其他未跟踪产物；本次只提交 `releases/0.1.43`。

## 三、等待 CI 镜像成功

必须确认**本次提交 SHA**对应的 `Build production image` 成功。两个仓库 push main 自动触发它；Agent Release 仓库没有这项镜像任务。

- 后端：<https://github.com/1nuo123/python-web-fastapi/actions/workflows/production-image.yml>
- 前端：<https://github.com/1nuo123/typescript-web-nuxt/actions/workflows/production-image.yml>

在两个 Actions 页面核对本次提交 SHA，再等待构建完成。不要把旧的绿色 run 当成本次成功。

CI 生成 `ghcr.io/1nuo123/python-web-fastapi:<完整SHA>` 和 `ghcr.io/1nuo123/typescript-web-nuxt:<完整SHA>`，服务器只拉取镜像，不现场构建。

## 四、登录服务器并更新

本机 PowerShell：

```powershell
ssh -i "$env:USERPROFILE/.ssh/aliyun_fastapi" root@39.96.201.189
```

以下为登录后的 **Bash**。先确保没有运行中的用户任务；这次升级 app、Agent 和 Caddy 会有维护中断，不承诺旧连接无损切换。不要并行启动第二次部署。

```bash
cd /opt/web/python-web-fastapi || exit 1
export PRODUCTION_FRONTEND_ROOT=/opt/web/typescript-web-nuxt
export COMPOSE_PROFILES=task-worker
unset BACKEND_IMAGE FRONTEND_IMAGE
bash deploy/production.sh doctor
# doctor 必须成功。现有脚本会检查环境文件、仓库、网络和 Compose。
```

将下面整段执行一次。它复用现有 update 入口；追加此次 Caddy 单文件挂载更新所需的校验和重建，不另造一套部署系统：

```bash
deploy_log="/root/codex-deploy-0.1.43-$(date +%Y%m%d-%H%M%S).log"
nohup bash -c '
  set -uo pipefail
  cd /opt/web/python-web-fastapi || exit 1
  export PRODUCTION_FRONTEND_ROOT=/opt/web/typescript-web-nuxt
  export COMPOSE_PROFILES=task-worker
  unset BACKEND_IMAGE FRONTEND_IMAGE
  result=0
  rollback_dir="/root/codex-rollback-0.1.43-$(date +%Y%m%d-%H%M%S)"
  install -d -m 700 "$rollback_dir" || exit 1
  cp deploy/caddy/Caddyfile.example "$rollback_dir/Caddyfile.example" || exit 1
  docker inspect fastapi-web-production-app-1 --format "{{.Image}}" > "$rollback_dir/backend-image-id" || exit 1
  docker inspect typescript-web-production-frontend-1 --format "{{.Image}}" > "$rollback_dir/frontend-image-id" || exit 1
  echo "ROLLBACK_DIRECTORY=$rollback_dir"
  bash deploy/production.sh update || result=$?
  caddy=(docker compose --project-name fastapi-web-production-caddy
    --project-directory /opt/web/python-web-fastapi/deploy/caddy
    --env-file /opt/web/python-web-fastapi/.env.production.local
    -f /opt/web/python-web-fastapi/deploy/caddy/compose.yml)
  if [ "$result" -eq 0 ]; then
    "${caddy[@]}" run --rm --no-deps caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile || result=$?
  fi
  if [ "$result" -eq 0 ]; then
    "${caddy[@]}" up -d --no-build --force-recreate --wait --wait-timeout 90 caddy || result=$?
  fi
  if [ "$result" -eq 0 ]; then bash deploy/production.sh status || result=$?; fi
  if [ "$result" -eq 0 ]; then curl --fail --silent --show-error --max-time 20 https://nuotop.xyz/health/ready || result=$?; fi
  printf "\nDEPLOY_EXIT_CODE=%s\n" "$result"
  exit "$result"
' >"$deploy_log" 2>&1 < /dev/null &
echo "$deploy_log"
tail -f "$deploy_log"
```

本段 Caddy 参数来自此次检查的实际线上 Compose（standard profile、单一 compose.yml、443入口）。如果之后调整了 resource profile 或 origin 8443 override，必须同步原 Compose 的 `-f` 参数，不得悄悄丢失 overlay。

`update` 会 fetch 两个 main、预拉取对应CI镜像、备份PostgreSQL、fast-forward仓库、按digest启动服务及迁移，再检查readiness。Caddy 的单文件 bind mount 可能仍指向 Git 更新前 inode，单纯 `up` 或向旧挂载 `reload` 不足以保证新文件生效；此次显式重建确保挂载新文件，会短暂断开入口连接。

只在日志出现 `DEPLOY_EXIT_CODE=0` 后进行功能验收；健康200不能替代实际登录、Agent连接和任务执行。SSH中断后重新连接只查看原日志，不再启动一次更新。
